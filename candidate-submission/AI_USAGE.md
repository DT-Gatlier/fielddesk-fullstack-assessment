## Details

1. **What I asked the tool to help with.**
   - Summarise the assessment and the grading weights, and propose an order of work.
   - Scaffold the monorepo, Docker setup, database schema and authentication.
   - Then: "do the task completely", meaning every feature in the brief, the tests and the documentation.

2. **Which parts were generated or substantially modified.** All submitted source was generated by the assistant:
   - SQL migrations, including the RLS policies, exclusion constraint and append-only triggers;
   - the Fastify API and the BullMQ worker;
   - the React frontend;
   - the integration and UI tests;
   - the Dockerfiles, Compose file and nginx config;
   - `README.md` and `TECHNICAL_NOTES.md`.

3. **What changed after the first output.** The assistant ran lint, type-check, builds and tests during the session and fixed what they found:
   - A form-field component put error text inside the `<label>`, which broke the input's accessible name. The UI test caught it, and the component was reworked to use `aria-describedby`.
   - Literal BOM characters in the CSV code were flagged by ESLint and replaced with `String.fromCharCode(0xfeff)`.
   - An upload pipeline used `.pipe()`, which does not propagate errors. It was replaced with `stream.pipeline` so oversized uploads cannot hang.
   - `npm audit` found advisories in Vitest 3 and React Router 6. Both were upgraded to patched majors.
   - _Add the changes you made yourself after review._

4. **How correctness, security and compatibility were verified.**
   - The backend suite runs against real PostgreSQL and Redis. It includes concurrency tests: simultaneous scheduling conflicts across two API instances, 10 simultaneous duplicate events, concurrent uploads against a quota, and repeated notification delivery. It also includes rollback, RLS and cross-tenant tests over HTTP and WebSocket.
   - Lint, type-check and build pass for both workspaces.
   - _Describe your manual checks, for example running the app with Docker Compose, logging in as both organisations, and trying to reach the other organisation's data by editing ids._

5. **Output rejected and why.**

   - Application-level locking for scheduling was rejected: a database exclusion constraint is correct across instances by construction.
   - A native `argon2` dependency was avoided in favour of built-in `scrypt`, so there is no native build step in Docker.
